# Design: `explain-code` — a reproducible code-comprehension skill

**Date:** 2026-08-18
**Status:** Approved for planning
**Author:** Shivaji Mukherjee (with Claude)

## Problem

Code generated by Claude arrives faster than it can be understood. Reading it
top-to-bottom teaches syntax but not intent; reading the docstrings teaches
intent but not mechanics. For a learner, the gap is widest at the seams — the
calls into `transformers`, `torch`, and other libraries, where the parameters,
return types, and shapes are governed by someone else's contract and are not
visible in the file at all.

Ad-hoc "explain this file" prompts produce inconsistent results: sometimes a
wall of text, sometimes a summary too shallow to act on, never the same shape
twice. Nothing persists, so the same file gets re-explained a week later.

## Goal

A reusable, personal-scope Claude Code skill that turns any source file into a
persistent, layered explainer document — consistent in structure, complete in
coverage, and verified against the running code rather than guessed.

Success looks like: pointing the skill at an unfamiliar file and, twenty
minutes later, being able to explain that file to someone else — including
what shape the data is at each step and which library owns which parameter.

## Non-goals

- Not an API-docs generator. Sphinx and pdoc already do that; they explain
  signatures, not concepts.
- Not automatic. No hook regenerates explainers on every edit — that fires
  during iteration, burns tokens on half-finished code, and produces noisy
  diffs.
- Not a whole-repo architecture document. One file at a time, invoked
  deliberately.
- Not a replacement for reading the code. The explainer is a companion to the
  source, not a substitute.

## Audience calibration

The reader is assumed to be learning, and the document serves three floors
cumulatively rather than picking one:

| Floor | Assumes | Explains |
|---|---|---|
| 1. Language mechanics | Can read English, has seen code | Python syntax and constructs, named on first appearance |
| 2. Data and shapes | Comfortable with Python | Types, shapes, dtypes, tensors, library contracts |
| 3. Design and why | Knows the domain basics | Design decisions, alternatives, failure modes |

This is why the document uses three passes rather than one merged narrative
(see Architecture). A single pass forces a choice of floor and loses the other
two.

## Architecture

### Packaging

A personal-scope skill, so it is available in every repository:

```
~/.claude/skills/explain-code/
  SKILL.md                        # procedure + quality bar (short, always loaded)
  references/
    document-template.md          # the full section-by-section output template
    python-constructs.md          # Pass 1 checklist of constructs to name
    diagram-recipes.md            # mermaid + ASCII shape diagram patterns
```

`SKILL.md` stays short so invocation is cheap. The reference files are read
only at the point in the procedure where they are needed — progressive
disclosure, matching the pattern used by the superpowers plugin skills.

### Invocation

```
/explain-code <path>
```

Single file per invocation. Writes to `docs/explainers/<basename>.md` relative
to the repository root, creating the directory if absent. The output path is
reported so the file can be opened immediately.

If the target repository has no `docs/` directory, the skill writes to
`explainers/<basename>.md` at the repository root instead, rather than
inventing a `docs/` tree in a project that does not use one.

### Verification requirement

Every claim about a runtime value — a type, a length, a shape, a dtype, a
return class — must be produced by executing code, not by inference. The skill:

1. Detects the project's interpreter (prefers `.venv/bin/python`, falls back
   to `python3`).
2. Writes a throwaway probe script to the scratchpad directory.
3. Runs it and reads real values into the document.

Before executing anything, the skill runs a pre-flight check on the target,
because importing a module runs its top-level code:

- **Top-level side effects** — module-level code that writes files, opens
  network connections, mutates a database, spawns processes, or reads
  credentials. If present, the skill does not import the module. It probes
  individual pure functions in isolation instead, or falls back to static
  description.
- **Cost** — code that downloads checkpoints, trains, or runs for more than a
  few seconds is not executed.
- **Scope** — probes may write only inside the scratchpad directory. A probe
  that would touch the project tree, the network, or any external service is
  not run.

This makes the rule symmetric: the skill refuses to guess, and it equally
refuses to find out by causing side effects. When either execution is
impossible (missing dependencies, GPU, credentials) or it is unsafe under the
checks above, the skill states the limitation inline rather than substituting
a guess:

> `> Not executed: requires a downloaded model checkpoint. Shape below is read
> from the transformers source, not observed.`

A guessed shape presented as fact is the primary way an explainer teaches
something wrong, so this rule is not optional.

### Completeness mechanism

Section 1 of every document is an inventory table of every module-level
symbol: imports, constants, functions, classes, and methods. That table is the
checklist — the skill verifies before finishing that each row is addressed in
at least one pass. This converts "explain everything" from an aspiration into
a checkable postcondition.

### Scale

Three full passes suit a file of roughly 50-300 lines. Outside that band the
skill adapts rather than producing something unusable:

- **Under ~50 lines** — passes collapse into one narrative. A trivial file
  does not need a six-section document, and padding it to fit the template
  teaches nothing.
- **Over ~400 lines** — the skill does not silently produce a 5,000-word
  document. It reports the size, proposes a split along the file's natural
  seams (a class, a group of related functions), and asks which unit to
  explain. Whole-file inventory and orientation are still produced, so the
  map exists even when the detail is scoped.

The band is a heuristic for the skill's judgement, not a hard check.

## Output document structure

```
# <filename> — explainer
> <relative path> @ <short git hash> · <N> lines · generated <date>

## 0. Orientation
    What problem this file solves — one paragraph, plain language.
    Where it sits: what imports it, what it imports. Callers are found by
    searching the repository, not assumed — some files (base classes,
    config modules, mixins) are close to meaningless read alone, and for
    those the caller list is the orientation.
    The one-sentence version.

## 1. Inventory
    Symbol table:  name | kind | signature | one-line purpose
    Import table:  package | what is used from it | why

    ─── PASS 1 · LANGUAGE MECHANICS ───

## 2. How the code is written
    Top-to-bottom walk. Every Python construct named and explained on first
    appearance only: module docstring, import forms, module constants,
    function definition, default arguments, class definition, __init__,
    __call__ and other dunders, self, comprehensions, slicing, tuple
    unpacking, truthiness, early return.
    Each entry: what the construct is in general, then what it does here.

    ─── PASS 2 · DATA AND SHAPES ───

## 3. What the data looks like
    Same walk, data lens. For every variable that holds data: its type, its
    structure, and a real example value obtained by execution.
    "Structure" is domain-dependent — see Data-contract vocabulary below.
    · ASCII diagrams where structure is positional (arrays, buffers, masks)
    · One mermaid flowchart of data movement through the file
    · Borrowed-API ledger (see below)

    ─── PASS 3 · DESIGN AND WHY ───

## 4. Why it is built this way
    Programming concepts actually in play, each pinned to a line number —
    named honestly, not padded. Design decisions and the alternatives
    rejected. Where the bugs hide and what this code defends against. How
    the tests pin the behaviour down.

## 5. Break it
    3–5 exercises: "change this line, predict what happens."
    Answers in a collapsed <details> block at the end.

## 6. Glossary
    Every piece of jargon used anywhere above, one line each.
```

### Data-contract vocabulary

Pass 2 asks "what does the data look like at this point". The right answer
depends on the domain, and the skill picks the vocabulary that fits rather
than forcing numeric framing onto code that has none:

| Domain | "Structure" means |
|---|---|
| Numeric / ML | shape, dtype, device, value range |
| Web / API | request and response schema, status codes, content type |
| CLI | argument grammar, exit codes, stdin/stdout format |
| Data processing | column names and types, row count, index, null policy |
| UI components | props and their types, state shape, event payloads |
| General | key set for dicts, element type for sequences, invariants held |

The requirement is constant — describe the real data concretely, with an
observed example. Only the vocabulary changes.

### The borrowed-API ledger

The section addressing the stated core need — understanding which parameters
and behaviours come from other packages:

| Call | Package | Returns | Parameters (theirs) | Parameters (ours) | Version risk |
|---|---|---|---|---|---|
| `tokenizer.apply_chat_template(...)` | `transformers` | `BatchEncoding` in 5.x, `list[int]` in 4.x | `tokenize`, `add_generation_prompt` | `messages` | High — return type changed between majors |

"Version risk" flags calls whose contract has changed or may change across
library versions. It is set to `unknown` when the library's history is not
established — an invented risk assessment is worse than an absent one. This is where silent breakage lives, and it is invisible
when reading the file alone.

### Diagram policy

- **Mermaid** for flow, relationships, and class structure. Renders natively
  on GitHub and in Claude artifacts.
- **ASCII** for tensor and array shapes. Mermaid renders these poorly, and a
  labelled band communicates a mask instantly:

```
labels:  [-100, -100, -100,   91,   15,  402,   88]
          └──── prompt ────┘  └───── answer ─────┘
             ignored by loss      graded
```

A diagram is included only when it carries information the prose cannot. No
decorative diagrams.

## Quality bar

The skill enforces five rules, checked before the document is written:

1. **Completeness** — every row of the inventory table is addressed in at
   least one pass.
2. **No repetition** — nothing is explained twice at the same level. Passes
   revisit the same code through different lenses, never the same lens twice.
3. **Executed, not guessed** — every runtime claim traces to a command that
   was run, or is explicitly labelled as unverified.
4. **No forward references** — no term is used before it is defined. The
   glossary is a backstop, not a substitute.
5. **Concrete over abstract** — real values and real numbers, never "some
   list" or "a tensor of the appropriate shape".

## Generality

The skill must work on any script, not only the numeric Python that motivated
it. Stating plainly what is universal and what is not:

**Universal — applies to any file in any language:**

- The six-section document structure
- The three-floor calibration (mechanics, data, design)
- The inventory table as a completeness postcondition
- The borrowed-API ledger — every language has library seams
- Break-it exercises, glossary, and all five quality-bar rules

**Parameterised by domain — the skill selects, the structure does not change:**

- Pass 2's vocabulary for "structure" (see Data-contract vocabulary)
- Whether ASCII shape diagrams apply at all — they suit positional data, and
  are omitted for code whose data is not positional
- Which concepts Pass 3 names, each pinned to a line number

**Language-specific — needs a reference file per language:**

- Pass 1's construct checklist. Python ships first, in
  `references/python-constructs.md`. Adding JavaScript or Go means adding a
  sibling file, not touching the procedure.
- The interpreter and probe mechanism used for execution.

For a file in a language with no construct checklist yet, the skill still
produces sections 0, 1, 3, 4, 5 and 6, and states in section 2 that a
checklist is unavailable — it does not improvise one, because a half-known
language produces confidently wrong syntax explanations, which is the worst
possible output for a learner.

**Not supported:** binary files, generated code, vendored dependencies, and
files over a few thousand lines. The skill says so and stops.

## Staleness

Each document header records the short git hash of the source file at
generation time. Drift is therefore visible by comparing that hash to the
current one. No automatic detection or regeneration in the first version —
re-running the command overwrites the document, which is the whole remedy.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Document is too long to read | Three passes are separately readable; orientation section stands alone at ~1 paragraph |
| Explainers drift from code | Git hash in header makes drift visible; regeneration is one command |
| Execution probe has side effects | Probe scripts are written to the scratchpad, are read-only with respect to the project, and are never committed |
| Skill guesses shapes when execution fails | Rule 3 requires an explicit unverified label; the failure is surfaced, not hidden |
| Pass 3 pads with concepts that are not really present | Every concept must be pinned to a line number, which makes padding visible |

## Deferred

- `ast`-based static inventory extraction, for files large enough that manual
  enumeration becomes unreliable.
- Whole-directory mode producing a connected overview document.
- Artifact publishing of a generated explainer.
- Automatic regeneration via a `PostToolUse` hook.
